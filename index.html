Abstract

We introduce a new task and benchmark dataset, VisEditBench, for understanding visual instructions in vector-format diagram editing. While recent advances have made progress in generating vector graphics from text or images, editing such diagrams remains relatively underexplored. Moreover, existing approaches predominantly rely on textual instructions, which are often unintuitive for specifying edits in structured visual content, particularly when users need to identify specific elements or indicate their spatial positions in a diagram. We propose visual instructions as a more intuitive interface for diagram editing, and construct a dataset of 694 samples with human-curated annotations overlaid on TikZ diagrams. The dataset covers multiple edit types as well as instructions with multiple editing operations. We evaluate 32 recent state-of-the-art multimodal models and observe consistent performance degradation for edits involving global layout or diagram structure, compared to local operations such as element deletion or modification. Furthermore, instructions that include multiple editing operations tend to result in lower performance than single-edit cases. Even recent models struggle to achieve consistently accurate edits, highlighting the inherent difficulty of the task. VisEditBench provides a valuable benchmark for advancing research on visually grounded diagram editing and structured visual understanding.

Task: Diagram Editing with Visual Instructions

Given an original diagram image Dorig, its TikZ code Corig, and a visual instruction image Ivis that overlays annotations such as arrows, sketches, and handwritten notes on Dorig, the model must produce modified TikZ code Cedit whose rendered diagram Dedit faithfully reflects the intended edits.

Visual instructions let users point at the exact element to change, or sketch where it should go, without writing a long description. To follow them, a model has to work out which element is targeted, what spatial relationship is intended, and where that element lives in the source code.

Input
  • Original diagram image Dorig
  • Original TikZ code Corig
  • Visual instruction image Ivis
Output
  • Edited TikZ code Cedit

Dataset Construction

Real-world diagram editing data is rarely recorded, so we build VisEditBench from existing TikZ diagrams in the Stack Exchange subset of DaTikZ-v2.

  1. Step 1: textual instructions and edited diagrams. Gemini 3 Pro Preview generates a textual editing instruction for each diagram, given a target edit type and a required number of edit operations (1–3). Several proprietary LLMs (Gemini 3 Pro Preview, GPT-5.2, GPT-5-mini, and Claude Sonnet 4.5) then apply the instruction to the TikZ code with minimal changes. Annotators checked 2,819 generated examples, and 2,148 (76.2%) met all quality criteria.
  2. Step 2: visual instructions. Annotators look at each original/edited diagram pair and draw a visual instruction on the original diagram in Excalidraw, either freehand (pen) or with built-in shapes (tool). The final dataset contains 694 triplets (Dorig, Ivis, Dedit), annotated by 18 annotators.

Evaluation

The final visual result matters most, so image-level evaluation is the primary measure and code-level evaluation is supplementary. Each image-level aspect is rated on a 5-point scale; if compilation fails, all three aspects get the minimum score of 1.

Image-level primary

IA — Instruction Adherence
How well the edited diagram follows the instruction.
CP — Content Preservation
Whether it avoids unintended changes beyond the instruction.
DR — Diagram Readability
Whether it stays readable, e.g., no overlapping elements or text.
FSR — Full-score Rate
Share of samples that score 5 on all of IA, CP, and DR.

Code-level supplementary

CFR — Compile Failure Rate
Share of generated code that fails to render.
IA / CP — on code
Instruction adherence and content preservation, judged from the diff of Corig, Cedit, and Cgen.
OES — Overall Edit Score
A holistic score combining code-level IA and CP.

MLLM-as-a-judge agrees with humans. Five Amazon Mechanical Turk workers rated each of 300 sampled outputs. Among the candidate judges, Gemini 3.1 Pro agreed most closely with human scores (Spearman's ρ = 0.843 / 0.813 / 0.793 for IA / CP / DR), so it serves as the judge for all main results. Inter-annotator agreement (Krippendorff's α) was 0.80, 0.67, and 0.65 for IA, CP, and DR, respectively.

  • Performance drops sharply with model size across the GPT, Claude, and Qwen3.5 families.

Analysis

Global edits are harder than local ones

Local edits such as REMOVE and UPDATE score high for many models, while LAYOUT and STRUCTURE edits are much harder, especially for weaker models. Failures there come from misreading the target, its spatial relationships, or the intended scope of the edit, and from failing to ground them in the right part of the source code.

More operations, lower scores

FSR generally falls as the number of edit operations grows. Gemini 3.1 Pro and Gemini 3 Flash change little.

The source code matters most

Removing the original TikZ code Corig causes the largest drop. Inferring and editing TikZ from the image alone remains difficult.

Visual instructions are harder to follow than text

Textual instructions beat visual ones for every model, though the gap narrows for stronger models. The model has to infer the target and scope from the annotations itself.

Editing code beats editing pixels

Code-based editing outperforms direct image editing within each model series. Gemini 3 Pro Image reaches 60.8 FSR, versus 12.0 for GPT Image 1.5 and 0.1 for Qwen-Image-Edit.

Verbalizing the visual instruction helps

Having the model first describe the visual instruction in text (Ivis → Îtext) improves FSR over Ivis alone in 15 of 16 model configurations. Gold textual instructions still do better overall.
